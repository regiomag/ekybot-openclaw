# Inter-Agent Runtime RFC

## Status

Draft V1

## Purpose

Define a deterministic, production-ready runtime for inter-agent communication in EkyBot.

This RFC exists to replace ad hoc mention handling with an explicit protocol driven by the platform and delivered through the connector.

## Goals

- Make inter-agent communication predictable for users.
- Remove duplicate visible replies.
- Enforce a stable publication order.
- Separate platform/system updates from agent-authored content.
- Make connector-based transport the official delivery path.
- Support new-user onboarding with a clear readiness check.

## Non-goals

- Arbitrary free-form agent orchestration.
- Unlimited multi-round loops between agents.
- Human-in-the-loop manual correlation for production flows.

## Terms

- `host agent`: the agent assigned to the source channel where the human is speaking.
- `target agent`: the agent explicitly mentioned by the human or selected by the runtime for a relay.
- `connector`: the local Companion/OpenClaw execution layer responsible for reliable delivery and local execution.
- `system message`: a platform-authored status/update message, not generated by an LLM prompt.

## Core principles

1. `target-first`
   The target agent reply must be published before any host summary about that reply.
2. `host-second`
   The host agent may summarize, acknowledge, or propose next steps only after the target result is known.
3. `single visible set`
   A single inter-agent turn may produce at most:
   - 1 system acknowledgement
   - 1 target reply
   - 1 host summary
4. `connector-official`
   Connector/Companion is the official transport and execution path for inter-agent delivery.
5. `system-owned status`
   Long-running progress and failure states are rendered by the platform, not improvised by agents.

## Required identifiers

Every inter-agent turn must carry the following identifiers end to end:

- `conversation_id`
- `request_id`
- `mention_id`
- `relay_id`
- `source_channel_key`
- `host_agent_id`
- `target_agent_id`
- `idempotency_key`

These IDs must be stable enough to correlate:

- notification creation
- relay enqueue
- connector claim
- target execution
- target publish
- host summary
- timeout/failure handling

## State machine

The runtime must persist an explicit state machine.

### States

- `queued`
- `sent_to_connector`
- `target_in_progress`
- `target_replied`
- `host_summary_pending`
- `host_summarized`
- `completed`
- `timeout`
- `failed`
- `cancelled`

### Transition rules

- `queued -> sent_to_connector`
- `sent_to_connector -> target_in_progress`
- `target_in_progress -> target_replied | timeout | failed`
- `target_replied -> host_summary_pending | completed`
- `host_summary_pending -> host_summarized | failed`
- `host_summarized -> completed`

No transition may skip directly from `queued` to `completed`.

## Publication contract

### System acknowledgement

Optional but recommended:

- publish exactly once when a valid relay is accepted
- examples:
  - `Transmission à Odin…`
  - `Odin répond…`

### Target reply

- published exactly once in the source channel
- authored as the target agent
- must be correlated to the same inter-agent turn

### Host summary

- published at most once
- only after `target_replied`
- should summarize outcome, next action, or completion
- must not restate the target reply in a misleading way

## Deduplication rules

Deduplication is required at three layers:

### 1. Backend event dedup

Keyed at minimum by:

- `mention_id`
- `target_agent_id`
- `step`

### 2. Connector execution dedup

Keyed at minimum by:

- `relay_id`

### 3. Publish dedup

Keyed at minimum by:

- `relay_id`
- `publish_step`

### Visible invariant

Users must never see duplicate target replies or duplicate host summaries for the same turn.

## Error handling

User-facing errors must be simplified into a small stable set:

- `Transmission en attente`
- `L’agent ciblé ne répond pas pour le moment`
- `Erreur technique, nouvelle tentative possible`

Detailed root causes remain internal:

- auth
- timeout
- duplicate drop
- gateway failure
- publish failure
- connector unavailable

## System messages

The platform may publish these standard system messages:

- `relay.accepted`
- `relay.in_progress`
- `target.reply_received`
- `host.summary_in_progress`
- `relay.timeout`
- `relay.failed`

These are system-authored and must not depend on prompt behavior.

## Host/target responsibilities

### Host agent

- may acknowledge the request locally only as a system message
- must not answer the substance of the target request before the target reply exists
- may summarize after target completion

### Target agent

- answers the requested task directly
- may request another round only through structured runtime actions, not ad hoc prose alone

## Multi-round extension

Multi-round inter-agent communication is out of scope for the first deterministic runtime, but the design must preserve room for:

- bounded depth
- bounded budget
- anti-loop protection
- final single user-facing summary

## Connector requirements

Connector must provide:

- reliable claim and execution of relay jobs
- idempotent retry semantics
- correlated logs using `relay_id`
- explicit timeout/failure reasons
- readiness/install validation for new users

## Onboarding requirements

A fresh user installing EkyBot + connector should be able to run one readiness check that validates:

- relay creation
- connector delivery
- target reply publish
- host summary publish

Result must be a clear PASS/FAIL report.

## Ownership split

### Codex

- runtime contract
- state machine
- publication ordering
- deduplication
- system message model
- user-facing inter-agent UX

### Eky

- connector hardening
- retry/timeout policy validation
- observability and rollout
- readiness/install validation
- production E2E verification

## Definition of done for V1

V1 is considered ready when:

- duplicate visible replies are eliminated
- target reply always precedes host summary
- system status messages replace raw 520-style user errors
- connector retries do not create duplicate visible publishes
- a fresh install can run a readiness check and get PASS/FAIL
